## Canary storage and logging

The intake canary test seeds a customer message, performs safety screening, reads the thread, creates a reviewed
reply proposal and returns a final answer. It verifies the intended draft contains the canary, while every persisted
step row and captured logs/stdout/stderr exclude it. Additional canaries target model-controlled metadata keys and
unknown tool names. Existing adapter tests cover sanitized provider failures, and copilot tests cover crash logging.

Allowed content-bearing locations are explicitly limited to their intended feature purpose:

- Original conversation message bodies and conversation notes intended for staff.
- Human-reviewed proposal revision payload text and supporting evidence excerpts; these are not step logs.
- `ai_runs.result`: the validated use-case output/final answer, with existing text caps.
- Owned copilot `assistant_messages.content`, returned to the owning staff user; assistant history is now fenced
  when sent back to a model.

Static prompt files and in-memory FakeGateway request captures are test/source artifacts. Complete prompts,
raw completions, customer free text and arbitrary model metadata must not appear in `ai_run_steps` or application
logs. The test proves literal canary absence for the exercised success/rejection paths; it is not a production
logging audit or proof against arbitrary encoded/covert channels.
