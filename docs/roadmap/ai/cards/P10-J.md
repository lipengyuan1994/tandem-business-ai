## Behavior and security reasoning

`demo_reviewer` is exactly admin minus `org.settings.write`, `org.business.write`, `org.location.write`
and `identity.membership.write`. It never gains `ai.settings.write`, `identity.owner.grant`, `audit.export`,
`admin_ops.data.manage` or `org.business.admin`. The policy version is 2026-11-07.1.
The judge can use the assistant and operate synthetic records, including approval of others' proposals,
booking and purchasing. Self-approval remains off; configuration, autonomy rules, AI settings and staff cannot change.
On an existing demo, the command first validates all three slugs and seeded ids, then ensures the same app user
as the seed and adds missing `demo_reviewer` memberships/grants, reactivating only the judge's membership if needed.
Existing linked subjects and all other app rows are preserved; repeat runs do not update existing app rows.
No seed/reset is needed or permitted as part of this login setup. Fixtures still provide the same user/memberships
on fresh installs and planned resets. Disabled app users or unexpected extra judge roles refuse for review.

The password is intentionally public, provided in `DEMO_JUDGE_PASSWORD` with the shipped length-12 minimum.
`demo-logins --judge` uses no random password, required action, password-update prompt or TOTP. It clears existing
non-password credentials, groups and all direct realm/client roles (including default composite roles), so the
account console has no manage-account/view-profile/manage-account-links authority; old Keycloak sessions are logged out.
Staff behavior stays unchanged.
Explicit password repair drops password/history first to reapply the same public value under passwordHistory(3).
Every repeat run rehardens the account; conflict identities and regulated/non-demo targets refuse.

`configure-demo-judge.py --demo` renders the environment value with JSON escaping into a public same-origin script.
The tracked asset is unconfigured (`null`); no password is hard-coded in Python. Only that public asset has a
commented gitleaks allowlist. The production theme mount is read-only; no container/service/dependency is added.
Both realm imports keep the default theme. Operators activate `tandem-demo` only on a synthetic demo using kcadm;
customer installs do not select it. CSP is unchanged; no inline or third-party script is introduced.

Existing AI token/daily/monthly budgets, concurrency and rate limits cap cost. Synthetic data only; SMTP must remain
unconfigured and email simulated. Judges share mutable operational records; this is not per-judge isolation.
Any future data reset is a separate explicit operator decision, never part of judge login setup. Account-console role removal does not independently verify all direct
Keycloak required-action/recovery links; live lockout tests must check these before public activation.
No new semantic model call is useful here: permission bundles and account policy are deterministic.
